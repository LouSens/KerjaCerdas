# Known Issues & Technical Debt

Engineering debt and open findings, each cited to a file so it can be checked directly against source. Items below are marked **Fixed** (with what changed), **Open** (still needs work, with why), or **Deferred** (deliberately not attempted this pass, with why).

## Deployment (Replit + Cloudflare Tunnel)

Findings from putting the current codebase behind a Cloudflare Tunnel in front of a Replit deployment.

- **Fixed — rate limiter misidentified every visitor as the same client behind the tunnel.** `_get_client_ip()` in `backend/app/api/middleware/rate_limiter.py` now trusts `CF-Connecting-IP` when `settings.trust_cloudflare_tunnel` is enabled (env: `TRUST_CLOUDFLARE_TUNNEL=true`) — Cloudflare's edge sets and overwrites this header, so it can't be spoofed by a client, unlike `X-Forwarded-For` (still never trusted). Only enable this flag if the origin is *exclusively* reachable through the tunnel. Covered by `TestClientIpResolution` in `backend/tests/unit/test_rate_limiter_concurrency.py`.
- **Fixed — `/docs`, `/redoc`, `/openapi.json` were unconditionally public.** `main.py` now gates all three behind `settings.is_production` via a request-time check (`_gate_docs_in_production`), returning 404 in production. Covered by `test_interactive_docs_are_gated_in_production` in `backend/tests/unit/test_caching_routing.py`.
- **Fixed — nothing caught a real Replit deployment missing `APP_ENV=production`.** `main.py`'s lifespan now raises at startup if `REPLIT_DEPLOYMENT` is set (which Replit sets automatically for a real deployment, independent of user memory) but `APP_ENV` isn't `production` — instead of silently keeping every dev-mode default (ephemeral JWT secret, public docs, in-band OTP codes) on something reachable from the public internet. Covered by `test_lifespan_rejects_a_real_replit_deployment_not_in_production` and `test_lifespan_allows_a_replit_deployment_correctly_configured` in `backend/tests/unit/test_api.py`. Note: `.replit`'s `[userenv.production]` already sets `APP_ENV=production`, so this is defense-in-depth, not a currently-firing bug.
- **Fixed — process-local rate-limit state under `autoscale`.** The Replit deployment intentionally stays on `autoscale` (not changed here). Given that, the rate limiter's in-memory counters previously would have silently multiplied every per-IP limit by the instance count (N instances → N× the intended budget) — each instance tracked its own counters with no shared state. `backend/app/api/middleware/rate_limiter.py` now supports a Redis-backed sliding window (`_RedisSlidingWindow`), shared across every instance, activated via `RATE_LIMIT_BACKEND=redis` + `REDIS_URL` pointing at a reachable Redis (e.g. Upstash — see [`ROADMAP.md`](ROADMAP.md)). It is **off by default** (`rate_limit_backend: str = "memory"`) so nothing changes until those two env vars are set, and it fails open to the existing in-process limiter (never a 500) if Redis itself is unreachable. Covered by `TestRedisSlidingWindow` and `TestRedisBackendIntegration` in `backend/tests/unit/test_rate_limiter_concurrency.py`, using `fakeredis` (no live Redis needed to verify the logic). **Remaining action:** provision `REDIS_URL` (Upstash free tier is sufficient to start) and set `RATE_LIMIT_BACKEND=redis` in the deployment's secrets — this is an infrastructure step, not a code change.
- **Open — the matcher's in-process query-embedding cache is still per-instance.** `backend/app/services/matching/matcher.py`'s in-process LRU is a pure performance optimization with a Postgres-backed second tier already in place (`query_embeddings` table) — a cache miss on one autoscale instance still hits the persisted tier before falling back to a fresh Gemini call, so this is a missed-optimization, not a correctness bug like the rate limiter was. Left as-is.
- **Open — CORS needs the tunnel's public hostname.** `_replit_origins()` already reads `REPLIT_DEV_DOMAIN`/`REPLIT_DOMAINS`, but a Cloudflare Tunnel typically fronts a custom or `trycloudflare.com` domain that is neither. Only matters if the SPA and API end up served from different origins through the tunnel (not needed if the API serves the built SPA itself, same-origin). Add the tunnel's hostname to `cors_allow_origins` if that split happens.

## Architecture

- **Fixed — dual domain-model drift.** `backend/tests/unit/test_schema_parity.py` now asserts every repository's Pydantic schema field set exactly matches its ORM model's column set, for all 11 registered repositories — the specific historical drift (`db.schemas.User` missing `name`) is closed and can't silently recur. Verified passing (`11 passed`).
- **Fixed — two divergent re-embed scripts.** `scripts/re_embed.py` (unrate-limited, no chunking, broken `sys.path` hack) is removed. `scripts/reembed.py` (settings-driven, chunked, rate-limited) is the one canonical implementation.
- **Fixed — hand-repeated employer/job ownership check.** `update_job`, `delete_job`, `find_candidates`, and `unlock_candidate` in `backend/app/api/routers/employer.py` each used to hand-roll "load the job, then check `job.employer_id == employer.id`" — a pattern a future endpoint could easily forget. All four now go through one shared `_require_owned_job()` helper, turning "correct everywhere currently checked" into "correct by construction."
- **Improved, not fully resolved — schema drift between `database/init.sql` and the ORM models.** The dump was missing the `applications.note` column and several newer tables (`otps`, `events`, `partnership_inquiries`, `query_embeddings`) that exist in `backend/app/db/models.py`. The missing column is patched directly in `init.sql` (verified against `models.py`'s `Application.note`). The missing *tables* were never actually a bug in practice — `init_db()`'s `create_all` fills in any table that doesn't already exist, it just can't add a column to a table `init.sql` already created — but it does mean `init.sql` will keep drifting on future model changes unless someone remembers to update it by hand. This dump only feeds the local `docker compose up` fresh-start path; the actual Replit/Supabase deployment path runs `alembic upgrade head` (wired into `.replit`'s `run` command) and never touches `init.sql`, so there's no live-data risk from the drift, only local-dev-experience risk.

## Database

- **Open — RLS is enabled but has no policies, and likely wouldn't take effect even with policies.** `backend/alembic/versions/45d873583ae4_enable_rls_for_supabase.py` turns on row-level security for the relevant tables but defines no `CREATE POLICY` statements. Deeper problem found while assessing this: Postgres row-level security is bypassed entirely by superusers, and by table owners unless `FORCE ROW LEVEL SECURITY` is also set — and this app's `effective_database_url` connects as a single shared role (`postgres` locally; whatever role the Supabase connection string uses in production) rather than a per-request, non-owner role. Writing policies without first confirming the app's DB role is a non-owner, non-superuser role (and setting `FORCE ROW LEVEL SECURITY`) would produce policies that silently do nothing — same blind spot as today, just with more code. Real RLS also doesn't fit every table here as a naive per-owner filter: `jobs` must stay readable across tenants for seeker-side matching to work at all, so any policy design needs to be scoped per-table, not applied uniformly. **Not attempted this pass** — this needs a role-separation decision (infrastructure, not just a migration) and a live Postgres to verify against, neither of which was available here. Tenant isolation for mutating endpoints continues to be enforced at the application layer (see the `_require_owned_job()` fix above), which is real and tested, just not defense-in-depth at the database level yet.

## Frontend

- **Fixed — `package.json` didn't declare its own test dependencies.** `vitest`, `@vitest/coverage-v8`, `@playwright/test`, and `msw` are now in `devDependencies` at the versions actually installed and used by the test suite; `frontend/package-lock.json` regenerated to match.
- **Fixed — two lockfiles coexisted.** `frontend/bun.lock` is removed; `package-lock.json` is canonical (matches the `npm`-based scripts used everywhere else — CI, README, replit.md).
- **Fixed — the "production" frontend image ran the Vite dev server.** `frontend/Dockerfile` is now a multi-stage build with explicit `dev` (Vite dev server + HMR, used by `docker-compose.yml` for local development) and `prod` (production `vite build` output served via `serve -s`, with SPA fallback routing) targets — neither is the implicit default; every caller must specify one. `docker-compose.yml` now builds with `target: dev`; `.github/workflows/release.yml`'s frontend image build now uses `target: prod`. This also fixes a latent bug where the `VITE_API_URL` build-arg passed by the release workflow was silently discarded (the old single-stage Dockerfile never declared or consumed it) — the new `build` stage does.
- **Deferred — test coverage is thin relative to surface area.** One unit-test file (`api.test.js`) and one e2e spec (`auth.spec.js`, login/register/rate-limit only) exist for 27 component files and a large global store. Matching UI, uploads, and verification flows have no automated coverage. Not attempted here — writing meaningful component/integration tests is a large, standalone effort, not a quick fix.

## Backend

- **Open — no per-domain API versioning.** `backend/app/api/main.py` mounts all 10 routers under one global `/api/v1` prefix. Low current impact (no breaking API change is planned); noted for later.
- **Deferred — no lockfile for backend Python dependencies.** `pyproject.toml` declares dependencies with lower-bound-only pins and there is no `poetry.lock`/`uv.lock`/`pdm.lock`. Not generated in this pass: none of `uv`, `poetry`, or `pip-tools` were available in this environment, and hand-writing a lockfile from a single machine's `pip freeze` would embed the wrong platform markers/hashes and be actively misleading rather than helpful. **Recommended next step:** install `uv` and run `uv lock` from `backend/`, then wire `uv sync --frozen` into CI and the Dockerfile.

## Production readiness

- **Superseded — manual VPS deployment.** `release.yml` still builds and publishes tagged images to GHCR for the Docker/VPS path, and `docker-compose.prod.yml` still exists — but the primary deployment path going forward is Replit + Cloudflare Tunnel, not a self-managed VPS. Keep the Docker path in sync opportunistically, or retire it explicitly once Replit is confirmed as the sole target.
