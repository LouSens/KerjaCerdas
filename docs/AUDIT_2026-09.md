# KerjaCerdas — Architecture & Technical Debt Audit

**Date:** 2026-09-05 · **Scope:** `backend/app`, `frontend/src`, root config/scripts
**Focus:** architectural scalability, routing flaws, and logic vulnerabilities — UI framework choice is explicitly out of scope and not evaluated.
**Method:** full read-only source review (no dynamic/pen-test pass); every finding below cites a file and line so it can be independently verified.
**Companion docs:** this audit complements, not replaces, `docs/FINAL_AUDIT_AND_PITCH_PLAN.md` (security/demo-integrity audit, same date) and the deleted-but-recoverable `docs/AUDIT_2026-08.md` (testing/security, git history). Where this pass found a status change since those docs were written, it is called out explicitly in §6.

---

## 1. Architectural Duplication (Critical)

**Dual domain-model definitions.** Every core entity is defined twice: once as a SQLAlchemy ORM class in `backend/app/db/models.py` (User, SeekerProfile, Employer, JobPosting, Application, Course, MatchBundle, SkillGapResult, ChatSession, AIPerformanceLog, GamificationStats) and again as a same-named Pydantic model in `backend/app/db/schemas.py`. This has already caused a real bug: `backend/app/api/routers/auth.py:67-71` carries an explicit workaround comment because the two "User" models silently disagree on which fields exist (`db/schemas.py`'s `User` has no `name` field; the ORM one does). Any future field added to one but not the other reproduces this class of bug.

**Two parallel schema sources of truth.** `database/init.sql` + `database/kerjacerdas.db` at the repo root are a static snapshot of the schema, while `backend/alembic/` (plus `backend/app/db/migrations/0001_init.sql`) is the actual migration-managed schema. `docs/FINAL_AUDIT_AND_PITCH_PLAN.md:24` already flags that the root dump has drifted (missing `applications.note`, no RLS policies) — confirmed still true in this pass. Two checked-in "sources of truth" for the same schema is a standing drift risk regardless of which one gets fixed first.

**Two divergent re-embed scripts.** `scripts/reembed.py` and `scripts/re_embed.py` both re-embed stale job/seeker vectors but with different implementations (one uses `backend.app.db.session`/settings properly with a `--all` flag and chunking; the other manually mutates `sys.path` and re-implements the same logic in half the lines). No comment marks either as canonical or deprecated — a maintainer could update one and never notice the other silently rotting.

**Frontend: route/view source-of-truth duplicated four times.** The mapping from a "view id" to a URL path is independently maintained in:
1. `frontend/src/App.jsx:38-80` (`VIEW_TO_PATH`/`PATH_TO_VIEW`)
2. `frontend/src/store/useStore.js:60-80` — an almost byte-identical copy, with a comment at line 59 admitting it "mirrors App.jsx"
3. `frontend/src/store/useStore.js:43-53` (`ALLOWED_VIEWS`, role → allowed-view-set)
4. `frontend/src/components/Sidebar.jsx:13-75` — the same view-id strings again, as navigation menu data

Nothing enforces these four stay in sync; `/harga` is a live example of drift (see §2). Adding, renaming, or removing a route today requires editing up to 4 files by hand.

## 2. Routing Flaws (High)

- **No per-domain API versioning.** `backend/app/api/main.py:149-161` mounts all 10 routers under one global `/api/v1` prefix. Fine today, but there is no mechanism to version a single domain independently if one router needs a breaking change later — the whole API would have to bump together.
- **Client-side-only route guard.** `frontend/src/App.jsx:110-115`'s `ProtectedRoute` checks `isAuthenticated`/`userRole` from the Zustand store, which is rehydrated straight from `localStorage` (`useStore.js:645-663`, persist key `kerjacerdas-v4`). There is no token-expiry re-validation before a protected route renders — real authorization still depends on the backend rejecting bad calls, but the *route layer* itself offers no server round-trip check.
- **Dead route entry.** `/harga` is declared in `PATH_TO_VIEW`/`VIEW_TO_PATH` and has a real `<Route>` (`App.jsx:161`), but that route immediately redirects to `/` — "pricing" is actually rendered as an anchor-scroll section on the home page (`useStore.js:205-217`). The route table advertises a page that never renders — a direct symptom of the duplicated source-of-truth in §1.
- **Authorization logic duplicated per-route instead of centralized.** `backend/app/api/routers/employer.py` re-implements the same "load resource, then check `employer.id == resource.employer_id`" ownership pattern by hand in every mutating endpoint (`find_candidates:275-281`, `unlock_candidate:361-365`, and similarly in job/application update endpoints) rather than as one shared FastAPI dependency. It is *currently correct everywhere it was checked in this pass* (see §6), but the duplication means a future endpoint can easily forget the check — there is no structural guarantee, only per-endpoint discipline.
- **Navigation authorization checked twice, inconsistently.** `App.jsx`'s `ProtectedRoute` and `useStore.js`'s `navigate()` (lines 195-240) both enforce the same role-allowlist independently, with different fallback behavior on denial (silent redirect vs. toast+modal) — a user can hit either path depending on how they got there.

## 3. Logic Vulnerabilities / Correctness (High–Medium)

- **Backend: N+1 queries.**
  - `backend/app/api/routers/employer.py:139-156` (`list_my_jobs`) — loops over every job for the employer and issues one `applications.find(...)` query per job inside the loop.
  - `backend/app/api/routers/employer.py:399-468` (`list_employer_applications`) — loops over applications and issues two extra queries per row (`repos.seekers.get`, `repos.users.find`).
  Neither is currently a demo-breaking issue at seed-data scale, but both degrade linearly with real data volume and are the first things that will show up in latency once the dataset grows past a handful of rows.

- **`backend/app/services/matching/matcher.py` — dead settings-driven weighting, in flux.** The module docstring states weights are "read from settings so they can be tuned via `.env` without a code change," and `SemanticMatcher._weights()` computes a fully normalized weight dict from `settings.matching_*_weight` — but neither `_weights()` nor `self._w` is ever called by the actual scoring code, which uses hardcoded literals instead. **This file currently has uncommitted, in-progress local changes** (paired with an uncommitted `README.md` update) that rewrite the hardcoded formula to `0.45` cosine / `0.25` skill / `0.15` experience / `0.10` education / `0.05` recency — i.e. the team appears to be actively deciding this formula should be fixed, not settings-driven. This audit intentionally does not touch `matcher.py` (see §6). **Open question for the team:** if the fixed-formula direction is final, delete the unused `_weights()`/`self._w` and the corresponding `MATCHING_*_WEIGHT` settings fields, and correct the module docstring and `settings.py`'s stated "no hardcoded weights" principle to match — right now the code, the settings layer, and the docstring each claim a different design.
- Same file: the region/location-matching block in `rank_jobs_for_seeker` is computed once as a soft boost and then recomputed identically a few lines later as a hard filter — pre-existing duplication, not touched here for the same in-progress-WIP reason.

- **Backend: mocked identity/OTP verification is live and auth-gated.** `backend/app/api/routers/verify.py` — NIK check is length-only (16 digits, any value passes), NPWP check is pattern-only, and OTP verification (`send_otp`) returns the code directly in the response body when `settings.otp_demo_enabled`. All are clearly labeled "demo mode" in responses and fail closed outside a correctly configured production environment, but they are real, callable, authenticated endpoints — a misconfigured `APP_ENV` is the only thing standing between "clearly a mock" and "silently providing zero identity assurance in production." (Already flagged in `docs/FINAL_AUDIT_AND_PITCH_PLAN.md`; repeated here because it is squarely a "logic vulnerability" for this audit's lens.)

- **Frontend: `EmployerPostJob.jsx` bypasses the shared API layer.** `frontend/src/components/EmployerPostJob.jsx:42-54` calls raw `fetch('/api/v1/employer/jobs', ...)` directly and manually reattaches `_authHeader()` — a `_`-prefixed (i.e. intended-private) helper imported from `services/api.js` — reimplementing what `services/api.js`'s exported `createEmployerJob` (line 198) already does, correctly, with the centralized 401/403/error-detail handling every other screen gets. `createEmployerJob` itself is consequently dead code (never called from anywhere).
- **Frontend: duplicated demo-data arrays present as real state.** `EmployerDashboard.jsx:191-197` and `EmployerJobs.jsx:110-115` each maintain their own `DEMO_JOBS` array, with *different* fake numbers for the same fictional listings, substituted in whenever the real job list is empty. A legitimately empty employer account is visually indistinguishable from a demo account, and a fix to one array's numbers won't propagate to the other.
- **Frontend: `JobPackUploader.jsx` double-handled its own store action's errors — fixed in this PR.** See §6.

## 4. Test & Config Debt (Medium)

- **No lockfile for backend Python dependencies.** `pyproject.toml` declares every dependency with a lower-bound-only pin (`fastapi>=0.110.0`, `sqlalchemy[asyncio]>=2.0.0`, `langgraph>=1.2.0`, `google-genai>=1.0.0`, …) and there is no `poetry.lock`/`uv.lock`/`pdm.lock` anywhere in the repo. Builds are not reproducible between environments or over time. The `langgraph`/`langgraph-prebuilt` pin comment (`pyproject.toml` ~lines 33-38) already documents one real incompatible-combo regression that was hit this way — nothing prevents a repeat with a different pair of packages.
- **`mypy --strict` is configured but likely not actually enforced.** Given the volume of `Mapped[list[Any]]` JSON columns in `db/models.py` and dynamic `getattr(...)` usage in `employer.py`, a genuinely strict run would surface many errors; whether CI runs it, and with how many suppressions, was not verifiable from source alone and should be checked directly (`mypy --strict backend/app`).
- **Frontend test coverage is close to zero relative to surface area.** One unit-test file (`api.test.js`, covering only the API client) and one e2e spec (`auth.spec.js`, login/register/rate-limit only) exist for 27 component files (~9,265 lines) and a 672-line global store — despite MSW, Playwright, and Vitest all being fully configured and ready to use. None of the recruiting pipeline, uploads, matching UI, or verification flows have any automated coverage.
- **`package.json` under/over-declares dependencies.** `zod` was declared but had zero usages anywhere in `src/` — removed in this PR (see §6). Conversely, `vitest`, `@playwright/test`, and `msw` are used by the test suite (imported directly in test files, driven via npm scripts) but were not present in `devDependencies` — the manifest does not accurately describe what the project's own test suite needs.
- **Two frontend lockfiles coexist** (`frontend/package-lock.json` and `frontend/bun.lock`, different last-modified dates) — signals inconsistent package-manager usage across contributors/environments and a real risk of two people installing different resolved dependency trees from the same `package.json`.

## 5. Minor / Style

- Stale "JSON store" docstrings/comments survived a storage-layer migration to `postgres_store.py` — fixed in this PR (see §6).
- Orphaned `.pyc` bytecode caches with no matching source file: `backend/app/db/__pycache__/json_store.cpython-31*.pyc` (no `json_store.py` exists), `backend/app/services/integrations/__pycache__/karirhub.cpython-31*.pyc` (no `karirhub.py` exists), `backend/app/api/__pycache__/models.cpython-31*.pyc` (models now live in `db/models.py`). Harmless (regenerated/ignored bytecode, not committed source) but a signal of incomplete cleanup after past refactors — worth a `find . -name '__pycache__' -exec rm -rf {} +` pass.
- Hardcoded fallback phone number `"+628123456789"` duplicated in two places in `employer.py` (`unlock_candidate` and `list_employer_applications`); a hardcoded fallback date string `"2026-08-26 10:00"` used when `applied_at`/`updated_at` are missing, rather than computed from `datetime.now()`.
- `frontend/src/components/_design.jsx` (a shared design-token/primitive module used by nearly every page) is filed and named like a component; `EmployerVerification.jsx` is a 12-line wrapper delegating to `VerificationDashboard.jsx`'s exported `VerificationScreen` — a reader looking for employer verification logic has to already know to open a same-named-but-different seeker file.

## 7. Recommended Next Priorities (not in this PR)

Ranked for post-audit follow-up, highest leverage first:

1. **Resolve the matcher.py weight-tunability question** (once current WIP lands) — either wire `_weights()` in for real, or delete the dead settings/docstring claim. Add a ranking-regression test asserting a weight change measurably shifts output, so this class of bug can't recur silently.
2. **Consolidate the frontend route/view map** into one shared module imported by `App.jsx`, `useStore.js`, and `Sidebar.jsx` — removes the 4-way duplication and the `/harga` dead-route class of bug structurally.
3. **Extract the employer resource-ownership check** into a shared FastAPI dependency instead of hand-repeating it per endpoint — turns "currently correct everywhere checked" into "structurally guaranteed."
4. **Fix the two N+1 query sites** in `employer.py` with batched lookups.
5. **Pick one schema source of truth** — retire either the root `database/init.sql` snapshot or treat Alembic as the only authority and regenerate the snapshot from it in CI.
6. **Reconcile the dual domain models** (ORM vs. Pydantic) — at minimum, add a test that fails if the two `User` definitions' field sets diverge again.
